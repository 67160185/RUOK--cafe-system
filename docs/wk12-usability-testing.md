# Week 12: Usability Testing — RUOK Cafe System

## ข้อมูลพื้นฐาน

- **กลุ่มเจ้าของ UI:** RUOK Cafe System (สมาชิกกลุ่มตาม [README.md](../README.md))
- **ผู้ทดสอบ:** `นายธนกฤต วิลาบุตร`
- **ผู้สังเกตการณ์:** นายพลเดช สุดศรี, นายธีรภัทร สุไลมาน, นายพิริยกร ชาตินาฝาย และนายนิภัทร เล็กขำ
- **วันที่ทดสอบ:** `29/10/2026`
- **ระบบที่ทดสอบ:** หน้าเว็บ RUOK Coffee ที่พัฒนาไว้จริงใน [`frontend/`](../frontend/) ไม่ใช่ Wireframe
- **สภาพแวดล้อม:** คอมพิวเตอร์และ Google
- **สถานะ:** เตรียมแผนและแบบบันทึกแล้ว — ยังไม่มีผลจากผู้ทดสอบจริง

> ก่อนเริ่มทดสอบ ควรเตรียมฐานข้อมูลที่มีพนักงาน เมนูที่สั่งได้ และประวัติการขายสำหรับหน้ารายงานไว้ให้พร้อม เพราะการสั่งซื้อจะทำให้สต็อกเปลี่ยนแปลง จึงควรใช้ข้อมูลทดสอบและเก็บข้อมูลตั้งต้นไว้เพื่อคืนสภาพหลังทดสอบ ไม่ควรใช้ข้อมูลจริงของร้าน

## 1. Task ที่ใช้ทดสอบ

ให้ผู้ทดสอบลองทำแต่ละเป้าหมายด้วยตนเอง โดยผู้สังเกตการณ์ไม่บอกตำแหน่งปุ่มหรือลำดับการกด ระบบที่พัฒนาจริงมีหน้ารับออเดอร์ จัดการเมนู และรายงานยอดขาย อย่างไรก็ตาม UI ปัจจุบันยังไม่มีตัวเลือกให้ผู้ใช้เปลี่ยนสาขา

| # | Task (บอกเป้าหมาย ไม่บอกวิธีกด) | เส้นทาง | Use Case / User Story | วัดผลอย่างไร |
|---|---|---|---|---|
| 1 | ลูกค้าสั่งเครื่องดื่ม 2 รายการ รายการหนึ่ง 2 แก้ว อีกรายการ 1 แก้ว และต้องการจ่ายเงินสด ช่วยบันทึกออเดอร์ให้ถูกต้อง | Happy path | UC-01 รับคำสั่งซื้อและคำนวณราคา / US-01 รับคำสั่งซื้อ / US-02 ชำระเงิน | ทำรายการสำเร็จหรือไม่ ใช้เวลาเท่าไร เลือกหรือแก้รายการผิดกี่ครั้ง และยอดรวมหรือวิธีชำระถูกต้องหรือไม่ |
| 2 | ลูกค้าสั่งเมนู 2 แก้ว แต่มีสินค้าเหลือเพียง 1 แก้ว ช่วยทำรายการให้ได้ตามจำนวนที่มี | Error path / Recovery | UC-01 รับคำสั่งซื้อ / US-01 รับคำสั่งซื้อ / US-04 อัปเดตสต็อก | ผู้ทดสอบสังเกตเห็นข้อจำกัดสต็อกและเข้าใจข้อความแจ้งเตือนหรือไม่ รวมถึงทำรายการต่อได้หรือไม่ |
| 3 | เปิดรายงาน แล้วบอกชื่อเมนูที่อยู่บนสุดในส่วน “เมนูขายดี” พร้อมจำนวนที่แสดง | Happy path | UC-07 ดูรายงานยอดขายและตรวจสอบสต็อก / US-06 ดูรายงานยอดขาย | หาหน้ารายงานเจอหรือไม่ ใช้เวลาเท่าไร และอ่านชื่อเมนูพร้อมจำนวนได้ถูกต้องหรือไม่ |

**เตรียมข้อมูลสำหรับ Task 2–3:** กำหนดให้เมนูสำหรับ Task 2 เหลือ 1 แก้ว และเตรียมประวัติการขายให้รายงานแสดงผล อย่าลืมบันทึกข้อมูลตั้งต้นไว้เพื่อคืนหลังทดสอบ หากเตรียมข้อมูลไม่ทัน ควรเลื่อนการทดสอบหรือสร้างฐานข้อมูลทดสอบใหม่ แทนการคาดเดาผลลัพธ์

**ข้อจำกัดของรายงาน:** UI เลือกสาขาแรกจากข้อมูลที่โหลด และส่วน “เมนูขายดี” แสดงยอดของสาขานั้นโดยไม่ได้กรองตามวันที่ที่เลือก ดังนั้นให้บันทึกคำตอบตามข้อมูลที่เห็น และอย่าสรุปว่ายอดที่แสดงเป็นยอดของวันนั้น

## 2. บันทึก Think-Aloud

ระหว่างทำ Task ให้ผู้สังเกตการณ์จดเวลา คำพูด และพฤติกรรมที่เกิดขึ้นจริง โดยไม่ชี้นำหรือช่วยกดแทน หากผู้ทดสอบติดขัด ให้จดสิ่งที่เกิดขึ้นไว้ก่อน แล้วค่อยถามคำถามปลายเปิดหลังจบ Task เช่น “เมื่อกี้คุณคิดว่าระบบจะทำอะไร”

## 3. รายการ Usability Issue

บันทึกเฉพาะปัญหาที่พบระหว่างทดสอบ พร้อมระบุคำพูดหรือพฤติกรรมที่สังเกตได้จริง ไม่สรุปเกินกว่าหลักฐานที่มี เรียงจาก Severity สูงไปต่ำ และระบุความถี่เป็นจำนวนครั้งเทียบกับจำนวนผู้ทดสอบ

ใช้เกณฑ์ต่อไปนี้ช่วยจัดระดับ Severity:

- **Critical:** ทำ Task หลักไม่สำเร็จ หรือระบบทำงานผิดพลาด
- **Major:** ทำสำเร็จแต่ใช้เวลานานผิดปกติหรือสับสนมาก
- **Minor:** ติดขัดเล็กน้อยแต่ยังทำ Task สำเร็จ
- **Cosmetic:** ความสวยงามที่ไม่กระทบการใช้งาน

### ข้อสังเกตที่เป็นจุดดี

- `[บันทึกพฤติกรรมที่แสดงว่าผู้ทดสอบใช้งานหรือกู้คืนจากข้อผิดพลาดได้ดี หากพบจริง]`

## 4. การแก้ไข / แผนการแก้ไข

กรอกส่วนนี้หลังสรุปผลทดสอบแล้วเท่านั้น หากยังไม่ได้ทดสอบ ให้ใช้สถานะ “รอผลทดสอบ” และอย่าระบุว่าแก้ปัญหาแล้ว หากยังไม่มีการแก้ใน UI จริง

| Issue # | Severity | สถานะ | รายละเอียดการแก้ไขหรือแผน (อ้างอิง UI ที่พัฒนาไว้จริงใน `frontend/`) |
|---|---|---|---|
| — | — | รอผลทดสอบ | ยังไม่มีผลทดสอบจริง จึงยังสรุป Issue หรือการแก้ไขไม่ได้ |

## 5. การใช้ AI

ใช้ AI ช่วยจัดโครงเอกสารและร่าง Task โดยอ้างอิง User Story กับฟังก์ชันที่ตรวจสอบได้จากระบบจริง ก่อนส่ง สมาชิกกลุ่มควรอ่านทวนและแก้ให้ตรงกับระบบที่ใช้งาน

AI **ไม่ได้** เป็นผู้ทดสอบหรือผู้สังเกตการณ์ และไม่ได้แต่งคำพูด พฤติกรรม ผลทดสอบ Usability Issue หรือรายการแก้ไขแทนผู้ใช้ ข้อมูลในหัวข้อ 2–4 ต้องมาจากการทดสอบจริงและบันทึกโดยสมาชิกกลุ่ม
