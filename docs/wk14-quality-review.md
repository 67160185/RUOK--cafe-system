# Week 14: Quality Review — RUOK Cafe System

## ข้อมูลการตรวจสอบ

- **ขอบเขต:** ตรวจ Routes, Controllers, Models, ตัวช่วย Validation ใน `src/` รวมถึง `schema.sql`
- **Checklist:** Input Validation, Authentication/Authorization และ IDOR, SQL Injection, Error Handling, Race Condition
- **จำนวน Endpoint:** 21 เส้นทางจากไฟล์ Routes 5 ไฟล์
- **ผลทดสอบอัตโนมัติ:** `npm test` ผ่าน 45/45 tests หลังเพิ่ม regression tests สำหรับการแก้ไขในรายงานนี้
- **ข้อจำกัด:** ชุดทดสอบใช้ฐานข้อมูลจำลอง จึงยังไม่ได้ทดสอบ race condition กับ MySQL จริงหรือทำ penetration test

### หลักฐานประกอบ Checklist

- **Input Validation:** Routes ตรวจชนิดและรูปแบบของ ID, วันที่, ราคา, จำนวน, วิธีชำระเงิน และ query ก่อนนำค่าไปใช้
- **SQL Injection:** ค่าจาก request ส่งเข้า query ผ่าน placeholder ของ `mysql2` ส่วน SQL แบบ dynamic ใช้เฉพาะ fragment ที่กำหนดไว้ในโค้ดและเลือกตามเงื่อนไขที่ตรวจแล้ว
- **Error Handling:** Error จาก async routes จะส่งต่อไปยัง error handler กลางใน `src/app.js` ซึ่งตอบกลับเป็น JSON โดยไม่เปิดเผย SQL error ให้ client ส่วน stock route จะแสดงข้อความผิดพลาดทั่วไปและบันทึกรายละเอียดไว้ฝั่ง server
- **Race Condition:** จุดที่ต้องอ่านแล้วเขียน เช่น สั่งซื้อ ปรับสต็อก ลบออเดอร์ และลบเมนู ใช้ transaction/row lock ส่วนปัญหาตอนย้ายเมนูข้ามสาขาแก้แล้ว แต่การสร้างหมวดหมู่พร้อมกันยังมีความเสี่ยงตามหัวข้อ 2

## 2. จุดที่พบความเสี่ยง

| # | ระดับ | จุดที่พบและผลกระทบที่อาจเกิดขึ้น | แนวทางแก้ไข / สถานะ |
|---|---|---|---|
| 1 | **High** | **ยังไม่มี Authentication/Authorization:** ใน [`src/app.js`](../src/app.js) มีการ mount API routes โดยไม่มีระบบ Login หรือกำหนดสิทธิ์ ผู้ที่เข้าถึงเซิร์ฟเวอร์ได้จึงอาจอ่านหรือแก้ข้อมูล รวมถึงส่ง `branch_id` ที่ต้องการมาเองได้ การกรองสาขาใน SQL ไม่ได้ยืนยันว่าผู้ใช้มีสิทธิ์ในสาขานั้น ขณะนี้ [`README.md`](../README.md) ระบุให้ใช้ระบบบนเครื่องพัฒนาเท่านั้น | **ยังไม่ได้แก้ในรอบนี้** — ก่อนเปิดให้ใช้นอกเครื่องพัฒนา ควรเพิ่มระบบ Login/Role และอ้างอิงสาขาจาก identity ฝั่ง server ไม่ใช่เชื่อ `branch_id` จาก request อย่างเดียว |
| 2 | **Medium** | **Race condition ตอนย้ายเมนูข้ามสาขา:** ก่อนแก้ `PUT /api/menu/:id` ตรวจประวัติใน `order_item` แล้วค่อยเปลี่ยน `branch_id` โดยไม่มี transaction หรือ row lock จึงอาจทำงานชนกับ `POST /api/orders` ที่กำลังสร้างออเดอร์เมนูเดียวกัน และทำให้ข้อมูลสาขาในประวัติออเดอร์ไม่สอดคล้องกัน | **แก้แล้ว** — ใน [`src/routes/menuRoutes.js`](../src/routes/menuRoutes.js) เพิ่ม `SELECT ... FOR UPDATE` และทำทั้งการตรวจประวัติกับการอัปเดตใน transaction เดียวกับการล็อกเมนูตอนสร้างออเดอร์ พร้อมเพิ่ม regression test ใน [`test/api.test.js`](../test/api.test.js) |
| 3 | **Medium** | **อาจสร้างหมวดหมู่ชื่อซ้ำเมื่อมี request พร้อมกัน:** `POST /api/categories` ตรวจชื่อซ้ำก่อน insert แต่ตาราง `category` ใน [`schema.sql`](../schema.sql) ยังไม่มี unique constraint ที่ `name` หากมีสอง request ใช้ชื่อเดียวกันในเวลาไล่เลี่ยกัน ทั้งคู่อาจผ่านการตรวจและเพิ่มข้อมูลซ้ำได้ | **ยังไม่ได้แก้ในรอบนี้** — ตรวจและจัดการข้อมูลซ้ำที่มีอยู่ก่อน จากนั้นเพิ่ม unique constraint ผ่าน migration และคงการตอบ `409` เมื่อเจอชื่อซ้ำ |
| 4 | **Low** | **พฤติกรรมของ HTTP Method อาจทำให้สับสน:** `PUT /api/menu/:id` รับบาง field และอัปเดตเฉพาะ field ที่ส่งมา (`COALESCE`) จึงทำงานคล้าย `PATCH` มากกว่า `PUT` ผู้เรียก API อาจเข้าใจว่า `PUT` ใช้แทนข้อมูลทั้ง resource | **ยังไม่ได้แก้ในรอบนี้** — คงพฤติกรรมเดิมเพื่อไม่ให้ client ที่ใช้อยู่มีปัญหา และพิจารณาเพิ่ม `PATCH` หรืออธิบาย contract ให้ชัดก่อนปรับ |

## 3. การแก้ไขและการทดสอบ

แก้ความเสี่ยงข้อ 2 โดยล็อกแถวเมนูตั้งแต่ตอนอ่านสถานะ ตรวจว่าเมนูมีอยู่และยังไม่เคยถูกสั่งก่อนย้ายสาขา ตรวจสาขาและหมวดหมู่ แล้วอัปเดตทั้งหมดใน transaction เดียวกัน หากตรวจไม่ผ่าน ระบบจะ rollback ก่อนตอบกลับ วิธีนี้ป้องกันไม่ให้การสร้างออเดอร์เข้ามาคั่นระหว่างการตรวจสอบกับการย้ายเมนู

นอกจากนี้ยังปรับ `PUT /api/orders/:id` ให้ล็อกแถวออเดอร์ด้วย `SELECT ... FOR UPDATE` แล้วตรวจพนักงานและอัปเดตภายใน transaction เดียวกัน เพื่อไม่ให้การลบออเดอร์ที่เกิดขึ้นพร้อมกันแทรกระหว่างตรวจสอบกับแก้ไข

เพิ่ม regression tests เพื่อตรวจว่า:

- การย้ายเมนูที่มีประวัติออเดอร์คืน `409`, ไม่ส่งคำสั่ง `UPDATE` และ rollback transaction
- การแก้ไขชื่อ/ราคาตามปกติยังสำเร็จและ commit transaction
- การแก้ไขออเดอร์ล็อกแถวก่อนตรวจพนักงานและ commit เมื่อสำเร็จ
- **ผลรวม `npm test`: ผ่าน 45/45 tests**

ชุดทดสอบตอนนี้ใช้ Fake DB จึงช่วยตรวจลำดับ transaction และพฤติกรรมของ route ได้ แต่ยังยืนยันการล็อกพร้อมกันบน MySQL จริงไม่ได้ ควรทดสอบกับ MySQL/InnoDB ก่อนนำไปใช้งานจริง

## 4. ความเสี่ยงที่ยังค้างและลำดับงานต่อ

1. **High — Authentication/Authorization:** ก่อนเปิดให้ผู้ใช้หรือเครือข่ายภายนอกใช้งาน ต้องมีระบบยืนยันตัวตน กำหนด Role และจำกัดสิทธิ์ตามสาขา
2. **Medium — ชื่อหมวดหมู่ไม่ซ้ำ:** ตรวจข้อมูลเดิมก่อนทำ migration เพิ่ม unique constraint และเพิ่ม test สำหรับกรณีชื่อซ้ำ
3. **Low — สัญญาการใช้ PUT/PATCH:** อธิบายพฤติกรรม API ใน OpenAPI หรือเอกสาร และวางแผนปรับโดยไม่ทำให้ client เดิมเสีย
4. ทดสอบ transaction/row locking และการใช้งานหลายสาขากับ MySQL จริง แล้วบันทึกผลแยกจาก automated tests

## 5. ขอบเขตและข้อจำกัด

การตรวจครั้งนี้ประกอบด้วยการอ่านโค้ดและรันชุดทดสอบ API อัตโนมัติ ไม่ใช่ penetration test และไม่ได้ทดสอบ Login เพราะระบบยังไม่มี นอกจากนี้ยังไม่ได้ทดสอบ race condition ทุกกรณีด้วยหลาย connection บน MySQL จริง ดังนั้นคำว่า “ผ่าน” ใน checklist หมายถึงพบกลไกที่เกี่ยวข้องจากโค้ดที่ตรวจ ไม่ได้หมายความว่าระบบปลอดภัยครบทุกด้าน
